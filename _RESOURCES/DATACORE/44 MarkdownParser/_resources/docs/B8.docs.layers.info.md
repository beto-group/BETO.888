## Modular Loading

**INFO**

Controls for dynamically importing sub-components, helper functions, or configuration modules from other files at runtime. This is the cornerstone of building composite applications, allowing you to break down a large application into smaller, manageable, and reusable pieces.

`dc.require` is the core function that powers this system. It can be used in two primary ways:

1.  **By targeting a specific, named code block** inside a Markdown file.
2.  **By importing the entire contents** of a `.js` or `.ts` file.

**Use when**

Your component becomes too large for a single file, you want to share utility functions across multiple components, or you need to build a main "app" that loads different "pages" or "views".

---

### Pattern 1: Importing from a Named Code Block (Recommended for `.md` files)

**Description**

This is the most robust and precise method for modularizing code that lives inside Markdown files. It combines `dc.headerLink` to create a stable reference to a specific section header with `dc.require` to load the code block under it.

The target code block must `return` an object containing the functions or components you want to export.

**Use when:**
*   Your reusable code is inside a `.md` file.
*   You want to keep multiple related but distinct modules inside a single documentation file.
*   You need a stable link that won't break if you add other content to the file.

**Code**

**1. Create the module file (`scripts/lists.md`)**
```markdown
# ListItem

This component renders a single list item.

```jsx
function ListItem({ text }) {
    return <li>Some text: {text}</li>;
}

// The return is essential. dc.require executes this block and gets this object.
return { ListItem };
```
```

**2. Import and use the module in another component**
```jsx
// --- In your main ViewComponent ---

// Use dc.headerLink to create a precise link to the # ListItem section.
const { ListItem } = await dc.require(
  dc.headerLink("scripts/lists.md", "ListItem")
);

function MyListView() {
    return (
        <ul>
            <ListItem text="whoa!" />
            <ListItem text="this is modular!" />
        </ul>
    );
}

return MyListView;
```

---

### Pattern 2: Importing an Entire File (Recommended for `.js` / `.ts` files)

**Description**

A simpler and cleaner pattern when your reusable code is in a dedicated JavaScript (`.js`) or TypeScript (`.ts`) file. You can `require` the file directly by its vault path. This is often preferred when working in an external IDE, as it provides better syntax highlighting and tooling.

**Use when:**
*   Your reusable code is in a `.js` or `.ts` file.
*   The entire file is intended to be a single, self-contained module.

**Code**

**1. Create the module file (`components/Module.jsx`)**
```jsx
// This file is components/Module.jsx
// Note the export syntax for a full JS file.
export function Module({ option1 }) {
    return <div>The option is: {option1}</div>;
}
```

**2. Import and use the module in another component**
```jsx
// --- In your main ViewComponent ---

// Directly require the .jsx file by its path.
const { Module } = await dc.require("components/Module.jsx");

function MainApp() {
  return (
    <Module
      option1='@page'
    />
  );
}

return MainApp;
```

## Application Flow

**INFO**

Patterns for orchestrating and managing the state of multiple child components to create a cohesive application experience.

**Use when**

Your application has multiple distinct screens or modes (e.g., a "list view" vs. a "detail view," or a "processor" vs. a "dashboard") and you need a central place to control the flow of data and UI state.

---

### Controller Component

**Description**

A main "controller" component that manages which child view is currently active and passes data down to it. This is the primary pattern for building multi-screen applications. It combines modular loading with local state management.

**Code (Pattern from `ReceiptTracker`)**
```jsx
// --- Main ViewComponent acting as a controller ---
const { useState, useEffect } = dc;

function AppController() {
  // 1. State to manage which view is active
  const [mainView, setMainView] = useState('processor'); // 'processor' or 'dashboard'
  
  // 2. Dynamically load the child view components
  const [ProcessorView, setProcessorView] = useState(null);
  const [DashboardView, setDashboardView] = useState(null);
  useEffect(() => {
    // Using the headerLink pattern for robustness
    const procPath = dc.headerLink("path/to/Processor.md", "ViewComponent");
    const dashPath = dc.headerLink("path/to/Dashboard.md", "ViewComponent");
    dc.require(procPath).then(m => setProcessorView(() => m.View));
    dc.require(dashPath).then(m => setDashboardView(() => m.View));
  }, []);

  if (!ProcessorView || !DashboardView) return "Loading views...";

  // 3. Conditionally render the active child component
  return (
    <div>
      <div className="view-tabs">
        <button onClick={() => setMainView('processor')}>Processor</button>
        <button onClick={() => setMainView('dashboard')}>Dashboard</button>
      </div>
      
      {mainView === 'processor' ? <ProcessorView /> : <DashboardView />}
    </div>
  );
}
```

## State Management

**INFO**

Controls for managing the internal state of your components, such as user input, UI toggles, and fetched data.

**Use when**

You need your component to be interactive and remember information across re-renders.

---

### Local State (`useState`)

**Description**

The fundamental React hook for adding state to a component. When the state is updated (via the `set` function), the component re-renders to reflect the change. This state is local to the component instance and is lost when the component unmounts.

**Signature**
```typescript
function useState<S>(initialState: S | (() => S)): [S, Dispatch<SetStateAction<S>>]
```

**Code**
```jsx
const { useState } = dc;

function Counter() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={() => setCount(currentCount => currentCount + 1)}>
        Increment
      </button>
    </div>
  );
}
```

## Applications

*   **Complex Composite Applications ( [[WORLD 888]], [[FITNESS EXPLORER]] )**
    *   Uses: `dc.require`, `dc.headerLink`, **Controller Component**. These are the most advanced examples of modularity. The main `WorldView` acts as a **Controller** that uses `dc.require` and `dc.headerLink` to load numerous sub-modules for distinct pieces of functionality (e.g., `WorldLogic`, `CharacterLogic`, `ScreenModeHelper`), keeping the main component clean and focused on orchestration.
*   **Multi-View Dashboards ( [[RECEIPT TRACKER]], [[CHATLLM]] )**
    *   Uses: **Controller Component**, `useState`. These components use the **Controller** pattern to switch between different screens. For example, `ReceiptTracker` uses `useState` to toggle between its "Processor" and "Dashboard" views. `ChatLLM` uses it to switch between the chat interface, settings panel, and history view.
*   **Modular Utilities ( [[CUSTOM FEED]], [[IFRAME PLAYER]], [[_RESOURCES/DATACORE/10 Kanban/KANBAN]])**
    *   Uses: `dc.require`. These components use `dc.require` to load shared helper modules. `CustomFeed` and `IframePlayer` load a shared `IframesGuidelines` configuration file, while the `Kanban` board requires a `FileEditor` utility module for its data handling.
*   **UI State Management ( [[DATACORE.flexilis.v4|DATACORE FLEXILIS]], [[CARD PICKER]])**
    *   Uses: `useState`. These components demonstrate extensive use of **`useState`** to manage all interactive aspects of their UI, including filters, column configurations, pagination state, and game progress. `CardPicker` also combines this with persistent state controls to save its game state across sessions.
