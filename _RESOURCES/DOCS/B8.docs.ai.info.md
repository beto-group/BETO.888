# MODULE 5 — INTEGRATIONS & APIs

This module provides the patterns and tools for connecting Datacore components to external services. This includes integrating with powerful AI models, leveraging the capabilities of other Obsidian plugins, and communicating with web services both on the local machine and on the internet.

> **Important Note:** This module covers a rapidly evolving area. The APIs for Large Language Models (LLMs) and other web services change frequently. The patterns documented here are robust, but the specific implementation details (like model names or API endpoints) may require updates over time. This section is expected to undergo major reworks as the technology matures.

---

## Catalog

*   **External API Controls** (Communicating with remote servers)
    *   **Core Request:** A robust wrapper for making web requests. (`fetchApi`)
    *   **LLM Integration:** Calling a Large Language Model for analysis or generation. (`callGroqLLM` pattern)
    *   **Serverless Webhook:** A fire-and-forget request to a simple endpoint. (`sendToWebhook` pattern)
*   **Local Service Controls** (Communicating with the user's machine)
    *   **Localhost API:** Querying a server running on the user's machine. (`getActivityWatchData` pattern)
    *   **Plugin Integration:** Accessing another Obsidian plugin's exposed API. (`getTextExtractorApi` pattern)
*   **Applications** (Examples to further explore)
	* **Examples** running within vault

## External API Controls

**INFO**

Controls for communicating with remote web servers over the internet. This is the foundation for integrating any third-party service that exposes an HTTP API, from weather data to cloud-based AI providers.

**Use when**

You need to fetch data from an external source, send data to a webhook for processing, or connect to a service like OpenAI, Groq, or Anthropic.

---

### `fetchApi`

**Description**

A robust wrapper for making web requests using Obsidian's built-in `requestUrl` function. It standardizes API calls by handling JSON parsing and basic HTTP status error checking, simplifying the process of fetching data from remote endpoints.

**Signature**
```typescript
async function fetchApi(url: string, options?: RequestUrlParam): Promise<any>
```

**Code**
```javascript
async function fetchApi(url, options = {}) {
  const requestUrl = dc.app.requestUrl || window.requestUrl;
  if (!requestUrl) throw new Error("Datacore's requestUrl is not available.");

  const response = await requestUrl({
    url,
    method: options.method || 'GET',
    ...options
  });

  if (response.status !== 200) {
    throw new Error(`Request failed, status ${response.status} for ${url}`);
  }
  return JSON.parse(response.text);
}
```

### LLM Integration

**Description**

A common pattern for sending a structured prompt to a Large Language Model API (like Groq, OpenAI, etc.) and parsing its JSON response. This pattern requires an API key, which must be managed securely and **never hardcoded** directly into component code.

Our standard approach is to store API keys as plain text files in a hidden vault directory, such as ex:`.datacore/.secrets/`, which is typically excluded from version control systems like Git. The component then reads the key from this file at runtime.

> **Security Note:** While this file-based method prevents keys from being exposed in code, the key itself is still stored in plain text. A future enhancement will investigate methods for encrypting these keys at rest within the vault for even greater security.

**Code (Pattern in Steps)**

This pattern consists of two main parts: securely loading the key, and then using that key to make the API call.

**1. Define the path and load the key**
```javascript
// Define the secure path for your API key
const API_KEY_PATH = ".datacore/.secrets/groq_api_key.txt";

// A helper to securely load the key from the vault
async function loadApiKey(path) {
  if (await dc.app.vault.adapter.exists(path)) {
    const key = await dc.app.vault.adapter.read(path);
    return key.trim();
  }
  return null;
}
```

**2. Make the API call with the loaded key**
```javascript
// The function to call the LLM, which takes the key as an argument
async function callGroqLLM(apiKey, promptText) {
  const payload = {
    model: "llama3-8b-8192",
    messages: [{ role: "user", content: promptText }],
    response_format: { type: "json_object" },
  };

  const response = await dc.app.requestUrl({
    url: "https://api.groq.com/openai/v1/chat/completions",
    method: "POST",
    headers: {
      "Authorization": `Bearer ${apiKey}`,
      "Content-Type": "application/json"
    },
    body: JSON.stringify(payload),
  });

  // The API often returns a JSON object where 'content' is a stringified JSON
  const responseData = JSON.parse(response.text);
  return JSON.parse(responseData.choices[0].message.content);
}
```

**3. Put it all together**
```javascript
// --- Example Usage ---
async function getJsonFromPrompt(prompt) {
  const apiKey = await loadApiKey(API_KEY_PATH);
  if (!apiKey) {
    new Notice("Groq API Key not found!");
    return;
  }
  
  try {
    const result = await callGroqLLM(apiKey, prompt);
    console.log(result);
  } catch (e) {
    new Notice("Failed to call LLM API.");
    console.error(e);
  }
}
```

### Serverless Webhook

**Description**

A "fire-and-forget" request pattern used to send data to a simple remote endpoint, like a serverless function (e.g., Cloudflare Worker). It uses `mode: 'no-cors'`, which allows sending data without complex CORS (Cross-Origin Resource Sharing) configurations. The trade-off is that the component cannot read the server's response body.

**Use when**

You need to dispatch an action (like sending a notification or logging an event) and only need to know if the request was sent, not what the server's specific response was.

**Code (Pattern from `Chatbot`)**
```javascript
async function sendToWebhook(url, data) {
  try {
    // Note: This uses the browser's `fetch`, not Obsidian's `requestUrl`.
    await fetch(url, {
      method: 'POST',
      mode: 'no-cors', // Key for simple, one-way communication
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify(data),
    });
    new Notice("Message dispatched successfully!");
  } catch (error) {
    // This catch block will only trigger on network failures, not server errors.
    console.error("Webhook failed:", error);
    new Notice("Failed to send message.");
  }
}
```

## Local Service Controls

**INFO**

Controls for communicating with services running on the user's own machine ("localhost"). This includes other applications that expose a web server or other plugins within the Obsidian ecosystem.

**Use when**

You need to build a dashboard for a local productivity tool (like ActivityWatch) or create a workflow that combines the functionality of multiple plugins (like OCR).

---

### Localhost API

**Description**

Fetching data from a web server running locally (e.g., on `http://localhost:5600`). The implementation is identical to the `fetchApi` pattern, but the URL points to a local address. This requires the user to have the target application running on their machine.

**Code (Pattern from `ActivityWatchDashboard`)**
```javascript
async function getActivityWatchData() {
  const AW_URL = "http://localhost:5600/api/0/query";
  const requestUrl = dc.app.requestUrl;
  
  // A query in ActivityWatch's specific query language
  const query = `
    aw_events = query_bucket("aw-watcher-window_localhost.localdomain");
    RETURN = aw_events;
  `;

  try {
    const response = await requestUrl({
      url: AW_URL,
      method: 'POST',
      contentType: 'application/json',
      body: JSON.stringify({ query }),
    });
    return JSON.parse(response.text);
  } catch (e) {
    new Notice("ActivityWatch server not running or unreachable.", 5000);
    return null;
  }
}
```

### Plugin Integration

**Description**

Accessing the API of another installed and enabled Obsidian plugin. The standard pattern is to check for the plugin's existence in `dc.app.plugins.plugins` using its unique ID (e.g., 'text-extractor') and then access its `api` object.

**Code (Pattern from `OCRReader` and `ReceiptTracker`)**
```javascript
// --- First, a helper to safely get the plugin's API ---
function getTextExtractorApi() {
  const plugin = dc.app?.plugins?.plugins?.['text-extractor'];
  if (plugin && plugin.api) {
    return plugin.api;
  }
  new Notice("Text Extractor plugin is not installed or enabled.", 5000);
  return null;
}

// --- Then, use the API to perform an action (e.g., OCR on a file) ---
async function performOcr(fileObject) { // Expects a TFile object
  const textExtractor = getTextExtractorApi();
  if (!textExtractor) return null;

  try {
    const text = await textExtractor.extractText(fileObject);
    return text || "No text could be extracted from this image.";
  } catch (e) {
    console.error("OCR process failed:", e);
    return `Error during OCR: ${e.message}`;
  }
}
```

## Applications

*   **Multi-Provider AI Interfaces ( [[CHATLLM]] )**
    *   The most advanced example of external API integration. It uses a dynamic version of the **LLM Integration** pattern, allowing the user to select from multiple providers (Groq, OpenAI, Ollama, etc.) and models. It relies on the core `fetchApi` pattern to communicate with each unique endpoint.
*   **Automated Data Processing Workflows ( [[RECEIPT TRACKER]] )**
    *   A powerful combination of local and external APIs. It uses **Plugin Integration** to call the Text Extractor plugin for OCR, then chains that result into an **LLM Integration** call to Groq's API to parse the raw text into structured JSON data.
*   **Local Application Dashboards ( [[ACTIVITYWATCH DASHBOARD]] )**
    *   A dedicated UI that uses the **Localhost API** pattern to fetch data from a running ActivityWatch server and visualize it within Obsidian.
*   **Simple Webhooks ( [[CHATBOT]] )**
    *   A minimalist component that demonstrates the **Serverless Webhook** pattern to send data one-way to an external endpoint without needing to process a response.
*   **Single-Purpose Plugin Tools ( [[OCR READER]] )**
    *   A clear example of the **Plugin Integration** pattern, acting as a simple UI wrapper around the more powerful Text Extractor plugin to provide an easy-to-use OCR interface.
