



# Windowing & Display Management [EA_windows]

This module provides the foundational patterns for controlling how and where components are rendered on the screen. It moves beyond simple inline views, enabling developers to create immersive, multi-window, and context-aware application experiences. These functionalities are broken down into two primary patterns.

---

### 1. Multi-Mode Display System

**What it does:** This pattern allows a single component instance to dynamically change its own container and presentation style, transitioning between different display modes. By leveraging a helper component, a view can be "popped out" from its default inline position to fill the entire Obsidian tab, the browser window, or even a native Picture-in-Picture (PiP) frame. The key is that the component's state is preserved because it is the same instance being moved and re-styled, not a new one being created.

**Key API Primitives:**

- <ScreenModeHelper>: A controller component that provides UI buttons and the logic for switching modes.
    
- helperRef.current.toggleMode(mode): An imperative function exposed by the helper to programmatically trigger a mode change.
    

**When to Use It:**

- When a component needs to offer an "immersive" or "focus" mode, like a 3D world or a distraction-free editor.
    
- To provide a 'pop-out' feature that expands a component to fill the available screen real estate for better usability.
    
- For integrating with native browser features like the Fullscreen API.
    

**Examples in Practice:**

- **World View** & **Views Control** (.../17 ViewsControl/, .../22 World888/): These are the primary examples. A <ScreenModeHelper> is rendered inside the main component's container.
    
    - The helper manages the logic to detach the main container (containerRef) from its original parent in the document.
        
    - It then re-parents the container to document.body and applies fixed positioning styles to make it fill the window (window mode) or enter browser fullscreen (browser mode).
        
    - It also handles reverting the component back to its original location and style when the mode is toggled off.
        
- **MarkdownEditor** (.../20 MarkdownEditor/): Implements a simple version of this pattern to toggle between a standard embedded view and a full-window "focus" mode for editing. This is a classic use case for maximizing the editing area without losing the component's state.
    
- **ActivityWatchDashboard** & **ReceiptTracker** (.../35 ActivityWatchDashboard/, .../43 ReceiptTracker/): Both of these complex dashboard components include a ScreenModeHelper. This allows the user to take the entire dashboard, with all its charts and tables, and expand it to fill the current Obsidian tab (fullTab mode), making detailed data easier to view and interact with.
    
- **License Agreement** (.../26 LicenseAgreement/): This component uses the ScreenModeHelper in a "locked" configuration (hideToggleButtons={true}). It forces the component into window mode upon appearing, effectively creating a modal overlay that captures the user's attention and cannot be switched to other modes from its own UI.
    

---

### 2. Dynamic Window Spawning ("FreshPip")

**What it does:** This is a more advanced pattern for creating new, fully independent floating windows at runtime. Unlike the multi-mode system, this pattern doesn't move the original component; it spawns a completely new instance of any specified component inside a draggable, resizable, and self-contained pop-up window. This is the foundation for building true multi-window applications within Obsidian.

**Key API Primitives:**

- spawnCustomPiP(filePath, header, functionName, options): The core function (exposed via ScreenModeHelper's helperRef) that initiates the creation of a new window. It uses dc.require internally to load the target component's code.
    
- <FreshPip>: The internal React component that renders the window frame, close button, and hosts the dynamically loaded component.
    

**When to Use It:**

- To create "in-app" pop-up windows, tool palettes, or secondary displays.
    
- To allow users to open and arrange multiple views or documents simultaneously in a freeform layout.
    
- For building complex applications where different modules need to be displayed and managed as separate visual entities.
    
- When one component needs to trigger the appearance of a completely different component in a floating window (e.g., a button that opens a music player).
    

**Examples in Practice:**

- **ViewsInceptions** (.../18 ViewsInceptions/): This component is the canonical example and a powerful debugging tool for this pattern.
    
    - It provides a UI with input fields for a file path, a header name, and a function name.
        
    - When the "Spawn" button is clicked, it calls spawnCustomPiP with these arguments.
        
    - The helper then creates a new <FreshPip> window, dynamically loads the requested component using dc.require, and renders it inside the floating container. This allows developers to pop out literally any other component into its own window.
        
- **World888** (.../22 World888/): The SpherePipSpawner uses this pattern to create an "inception" effect. When a user clicks on an interactive sphere within the 3D world, it calls spawnCustomPiP to open another, separate instance of the WorldView component in a new floating window.
    
- **MobileMusicPlayer** (.../39 MobileMusicPlayer/): This demonstrates a practical application where a simple, minimal UI element (a button in the corner of the screen) acts as a trigger. Clicking it calls the logic to spawn the full MusicPlayer component inside a floating "FreshPip" window, providing an on-demand, sophisticated UI.
    
- **MusicPlayer** (.../36 MusicPlayer/): This component uses a custom, non-reusable implementation of this pattern called PipHelper. While it doesn't use the generic FreshPip spawner, it follows the same core principle: when the user clicks the PiP button, it programmatically creates a new, draggable <div> element, appends it to the document.body, and renders a minimal player interface inside it. This shows a bespoke application of the floating window pattern.
