






# Resources, Assets, & External Libraries

This module covers the foundational patterns for loading and managing the resources a component needs to function. This includes dynamically loading large, third-party JavaScript libraries from the web (with caching for performance and offline use) and resolving paths to local media assets within the vault so they can be rendered in web-based views.

---

### 1. External Library Loading & Caching

**What it does:** This pattern dynamically loads large, third-party JavaScript libraries (like D3.js, Babylon.js, or Ace Editor) from a CDN at runtime. The advanced version of this pattern also caches the downloaded library as a file within the vault's hidden .datacore directory. This enables significantly faster loads on subsequent uses and allows the component to function even when the user is offline.

**Key API Primitives:**

- loadScript(src, onload): A utility function that creates a <script> tag and appends it to the document to load a library.
    
- dc.app.vault.adapter: The file system adapter used to check for, read from, and write to the local script cache.
    
- fetch(src): Used to download the script content from the CDN before caching it locally.
    

**When to Use It:**

- When your component depends on a large external library that you don't want to bundle directly into the component's code.
    
- To improve initial load times by deferring the download of heavy dependencies until they are actually needed.
    
- To provide offline functionality for components that would otherwise require an internet connection.
    

**Examples in Practice:**

- **LoadScript Component** (.../28 LoadScript/): This component is the canonical implementation of the advanced caching pattern.
    
    - The loadScript function first checks if the source src is a URL.
        
    - It generates a safe filename and checks for its existence in the .datacore/script_cache directory.
        
    - If the file exists, it reads the content directly from the vault (adapter.read).
        
    - If not, it uses fetch to download the script, then writes it to the cache path (adapter.write) before executing it.
        
    - The CodeEditor v1, MapGlobe, and D3JSTest components all dc.require and use this exact loadScript utility to manage their dependencies.
        
- **LottieExperiment**, **Image Render**, **Aquarium**: These components use a simpler, non-caching version of loadScript. They check if a global variable (e.g., window.Fuse, window.customElements.get("lottie-player")) exists, and if not, they call a basic loadScript to fetch the library from a CDN. This is effective but requires an internet connection on first run.
    
- **BabylonLocal**, **GameEngineBuild**: These components also use the simpler, non-caching loadScript pattern to pull in their respective 3D engines (Babylon.js, Lottie) from CDNs.

### 2. Local Asset Path Resolution & Rendering

**What it does:** This pattern is essential for displaying local vault assets (images, videos, 3D models, sound files, animations) within a web-based view. It involves finding the target asset file—often using a flexible, typo-tolerant "fuzzy search"—and then converting its vault-relative path into a special, web-accessible URL (e.g., obsidian://... or a blob URL) that can be used in the src attribute of HTML elements like <img>, <audio>, or in a 3D engine's texture loader.

**Key API Functions:**

- app.vault.getFiles(): Gets a list of all files in the vault to be used as the source for a search.
    
- new Fuse(files, { keys: ["name"] }): Initializes the Fuse.js fuzzy search library.
    
- app.vault.getResourcePath(file) or app.vault.adapter.getResourcePath(path): The core Obsidian API function that generates the web-accessible URL for a local file.
    
- URL.createObjectURL(blob): Used to create a temporary, web-accessible URL from in-memory binary data (e.g., after reading an image with readBinary).
    

**When to Use It:**

- Any time you need to display a local image, SVG, or Lottie animation.
    
- For loading local .glb or other 3D model files into a Babylon.js or WebGL scene.
    
- To set the source for local audio or video files in <audio> and <video> elements.
    
- When you want to reference assets by a simple filename without hardcoding the full, brittle path.
    

**Examples in Practice:**

- **Image Render**, **LottieExperiment**, **LoadingLogo**, **Aquarium**: These components are prime examples of the fuzzy search and resolve pattern. They define a helper function requireMediaFile which:
    
    1. Uses fuzzyFindFile (powered by Fuse.js) to locate a file like "obsidian_lottie.json" or "BETO_Logo_W_Loading.svg" anywhere in the vault.
        
    2. Takes the resulting file object and passes it to app.vault.getResourcePath() to get the final src URL for the <lottie-player> or <img> tag.
        
- **GameEngineBuild** & **BabylonLocal**: These 3D components use the same pattern to load textures and models.
    
    - GameEngineBuild's loadTexture function takes a URL generated by requireMediaFile to apply an image from the vault as a texture to a 3D object.
        
    - BabylonLocal does the same to get the resource path for a .glb file, which is then passed to BABYLON.SceneLoader to load the 3D model.
        
- **SoundPlayer** & **Animated Card**: These components use direct path resolution for audio/video assets.
    
    - SoundPlayer gets the audioSrc by passing a hardcoded path (_RESOURCES/.../soundtrack.wav) directly to app.vault.adapter.getResourcePath().
        
    - Animated Card does the same for a list of video files, loading each one into a VideoTexture for playback on the 3D card face.
        
- **OCRReader** & **ReceiptTracker**: These components demonstrate creating blob URLs from binary data. They read an image file from the vault using dc.app.vault.readBinary(file), create a new Blob(...) from the resulting ArrayBuffer, and then generate a temporary preview URL with URL.createObjectURL(blob) for display in an <img> tag.
