


# File System Operations: Functional Patterns & Examples

This section breaks down the core functionalities provided by the File System Operations API. Each pattern describes a specific development goal, lists the key API functions used to achieve it, and provides examples of components that implement the pattern.

---

### 1. Live File Editing & Manipulation

**What it does:** This pattern involves directly reading, writing, and modifying the content of user-facing Markdown files within the vault. It's the foundation for creating dynamic applications where the UI is a direct reflection of, and can change, the content of notes.

**Key API Functions:**

- readFile(path)
    
- writeFile(path, content)
    
- updateFrontmatter(path, patch)
    
- applyEdits(path, edits)
    
- Legacy/Obsidian Native: app.vault.read(file) and app.vault.modify(file, content)
    

**When to Use It:**

- When your component's state should be stored in human-readable Markdown.
    
- For creating in-place editors for notes or sections of notes.
    
- When a user action in the UI needs to add, remove, or change text in a file (e.g., checking off a task).
    
- For building systems where notes themselves are the database (e.g., Kanban cards as text blocks).
    

**Examples in Practice:**

- **Kanban Board** (_RESOURCES/DATACORE/10 Kanban/): This is a prime example. Each card on the board is a distinct text block within a Markdown file. When a user drags a card from the "To Do" column to the "Done" column, the component performs two file operations: it reads ToDo.md, removes the corresponding text block, and then reads Done.md to append that text block, saving both files with app.vault.modify.
    
- **Custom Feed** (_RESOURCES/DATACORE/5 CustomFeed/): The feed is populated by parsing sections of a source Markdown note. The component features an "Edit" mode that allows the user to change the content of a section directly. On save, it uses editFileSegment (a wrapper for app.vault.modify) to update the source note with the new content.
    
- **Markdown Editor** (_RESOURCES/DATACORE/20 MarkdownEditor/): The entire purpose of this component is to provide a custom editing experience. It uses getRawContent (app.vault.read) on load and setRawContent (app.vault.modify) to save any changes the user makes.
    
- **License Agreement** (_RESOURCES/DATACORE/26 LicenseAgreement/): To track user consent, this component reads a specific .md file containing a list of tasks. When a user checks a box, the component reads the file, finds the corresponding line (e.g., - [ ] I agree), changes it to - [x] I agree, and writes the entire file back using app.vault.modify.
    
- **Receipt Tracker** (_RESOURCES/DATACORE/43 ReceiptTracker/): After processing a receipt image, this component **creates a new Markdown file** in the _Processed folder. It uses app.vault.adapter.write to save a new note containing the extracted data in both YAML frontmatter and JSON/text code blocks.

### 2. State Persistence to Vault (.datacore directory)

**What it does:** Saves and loads a component's internal state (like settings, user data, history, or progress) to a dedicated JSON file, typically stored in the vault's hidden .datacore directory. This allows the component's experience to be persistent across sessions and reloads without cluttering the user's workspace.

**Key API Functions:**

- loadState<T>(key, defaults)
    
- saveState<T>(key, value)
    
- statePath(key)
    
- readJson<T>(path) / writeJson<T>(path, data)
    

**When to Use It:**

- To remember user settings (e.g., theme, volume, API keys).
    
- To save progress in a game or complex workflow.
    
- To store application history (e.g., chat logs, drawn cards).
    
- For any data that is essential to the component's function but is not meant to be edited directly by the user as a Markdown note.
    

**Examples in Practice:**

- **ChatLLM** (_RESOURCES/DATACORE/42 ChatLLM/): Persists the entire application state. This includes the list of all conversations (chat history), user-configured provider settings (API keys, models), and UI state. It saves this complex state to a JSON file under .datacore, ensuring that chats and settings are never lost.
    
- **Canvas v1** (_RESOURCES/DATACORE/23 Canvas/): Saves the complete state of a canvas—including the position, size, color, and content of every object—to a JSON file. This allows users to create complex visual layouts and have them perfectly restored the next time they open the view.
    
- **Card Picker** (_RESOURCES/DATACORE/40 CardPicker/): At the end of every turn, it saves the current state of the game—the remaining cards in the deck, the history of drawn cards, and the current score—to a JSON file. This provides a seamless "save on exit" experience.
    
- **Music Player / Mobile Music Player** (_RESOURCES/DATACORE/36 MusicPlayer/, _RESOURCES/DATACORE/39 MobileMusicPlayer/): Uses FileUtils.saveLikedSongs to write a list of a user's favorite tracks to .datacore/musicplayer/liked-songs.json. This ensures liked songs persist between sessions.

### 3. Local Asset Path Resolution

**What it does:** Generates a special, web-accessible URL (e.g., obsidian://... or a blob URL) for a local file in the vault. This is essential for allowing web technologies like <img>, <audio>, <video>, or 3D engines to load and display local media assets that are stored within the Obsidian vault.

**Key API Functions:**

- resolveAssetUrl(path)
    
- Legacy/Obsidian Native: app.vault.getResourcePath(file) or app.vault.adapter.getResourcePath(path)
    

**When to Use It:**

- To display an image from your vault in an <img> tag.
    
- To provide the src for an <audio> or <video> player.
    
- To load a 3D model (.glb) or texture file in a Babylon.js or WebGL scene.
    
- To load a Lottie animation .json file in a <lottie-player>.
    

**Examples in Practice:**

- **ImageRender** / **LottieExperiment** / **LoadingLogo** (.../11 ImageRender/, .../12 LottieExperiment/, .../31 LoadingLogo/): These components all use a getMediaResourcePath helper. This function finds a file (often with a fuzzy search) and then calls app.vault.getResourcePath(file) to generate a URL that can be assigned to the src attribute of an <img> or <lottie-player> element.
    
- **Sound Player** (.../32 SoundPlayer/): Directly uses app.vault.adapter.getResourcePath(songPath) to get a playable URL for a .wav file and sets it as the src for an HTML <audio> element.
    
- **Animated Card** (.../34 AnimatedCard/): This component uses local videos as a "live texture" on a 3D model. It resolves the path for each video file using the asset resolution API to get a URL that the Babylon.js video texture engine can consume.
    
- **BabylonLocal** (.../25 BabylonLocal/): Loads a local .glb 3D model file by first resolving its vault path into a web-accessible URL, which is then passed to the Babylon.js scene loader.
    
- **Receipt Tracker** (.../43 ReceiptTracker/): To show a preview of the selected receipt, the component reads the image file as binary data (app.vault.readBinary), creates a Blob from it, and then generates a temporary local URL using URL.createObjectURL(blob). This achieves the same goal of making a local file displayable in an <img> tag.
