




# AI / INTEGRATIONS & APIS

This module provides the patterns and tools for connecting Datacore components to the outside world. This includes interacting with external web services, leveraging the capabilities of other Obsidian plugins, and integrating with powerful AI models for content generation and analysis.

---

### 1. External LLM API Integration

**What it does:** This pattern involves sending data (text, images, or structured prompts) to external Large Language Model (LLM) providers like Groq, OpenAI, or Google Gemini. The component typically constructs a request, sends it via a network call, and then parses the structured JSON response from the AI to use within the application.

**Key API Functions:**

- Browser fetch API or dc.app.requestUrl for making HTTP requests.
    
- JSON.parse() to process the text response from the LLM into a usable JavaScript object.
    

**When to Use It:**

- For intelligent data extraction from unstructured text (e.g., parsing details from a receipt).
    
- To build conversational chat interfaces.
    
- For content generation, summarization, or reformatting tasks within a component.
    
- Whenever you need to leverage the analytical or generative power of a modern AI model.
    

**Examples in Practice:**

- **Receipt Tracker** (.../43 ReceiptTracker/): A sophisticated, multi-step implementation of this pattern.
    
    1. First, it gets raw text via the OCR pattern (see below).
        
    2. It then constructs a highly specific prompt (EXTRACTION_PROMPT) that instructs a Groq Llama3 model on how to parse the text and what JSON schema to use for the response.
        
    3. The analyzeTextWithGroq function makes a fetch call to the Groq API endpoint.
        
    4. It includes a robust mechanism for managing and rotating through multiple API keys, automatically trying the next key if one fails due to rate limits or other errors.
        
    5. Finally, it parses the JSON text from the AI's response to populate its data fields.
        
- **ChatLLM** (.../42 ChatLLM/): This component is a full-featured interface built entirely around this pattern. It provides a UI for managing API keys and settings for numerous providers (OpenAI, Gemini, Ollama, etc.). It constructs a message history payload and sends it to the selected provider's API, then renders the Markdown response from the AI in the chat window.

### 2. Local Plugin Integration (OCR)

**What it does:** This pattern demonstrates how a Datacore component can act as a client to another installed Obsidian plugin, using that plugin's exposed API to perform a specialized task. This avoids reinventing functionality that already exists within the Obsidian ecosystem. The primary example is Optical Character Recognition (OCR).

**Key API Functions:**

- app?.plugins?.plugins?.['text-extractor']?.api: The standard method for accessing the API of an enabled community plugin.
    
- textExtractorApi.extractText(file): The specific function call to the Text Extractor plugin to perform OCR on a local image file.
    

**When to Use It:**

- When you need to perform a specialized task (like OCR, calendar integration, etc.) that another plugin already does well.
    
- To create powerful workflows that chain the functionality of multiple plugins together.
    
- To provide a custom UI for another plugin's backend functionality.
    

**Examples in Practice:**

- **OCRReader** (.../41 OCRReader/): A direct and clear implementation. It first checks if the Text Extractor plugin is available using getTextExtractor(). If it is, it allows the user to select an image from the vault and then calls textExtractorApi.extractText() on the selected file to display the recognized text.
    
- **Receipt Tracker** (.../43 ReceiptTracker/): Uses this pattern as the critical first step in its processing pipeline. The performOcr function is called on a receipt image. The raw text string returned by the Text Extractor API is then passed directly to the External LLM API Integration pattern for analysis and JSON structuring.

### 3. Local Server API Integration

**What it does:** This pattern involves connecting to and fetching data from a web server running on the user's local machine (localhost). This is used for integrating with companion applications or local data services that expose an HTTP API.

**Key API Functions:**

- fetch() or dc.app.requestUrl pointed at a http://localhost:PORT address.
    

**When to Use It:**

- To build dashboards for local productivity tools like ActivityWatch.
    
- For connecting to local development servers or databases.
    
- To create an interface for any self-hosted application that provides web endpoints.
    

**Examples in Practice:**

- **ActivityWatchDashboard** (.../35 ActivityWatchDashboard/): This component is entirely built on this pattern. It makes numerous fetch calls to the local ActivityWatch server, which runs by default on localhost:5600. It hits various endpoints (e.g., /api/0/buckets, /api/0/query) to pull raw event data, which it then processes, categorizes, and visualizes within the dashboard UI.

### 4. Webhook / Serverless Function Integration

**What it does:** This pattern is used for sending data to a simple, remote HTTP endpoint, often a serverless function (like a Cloudflare Worker) or a webhook. The communication is typically "fire-and-forget," where the component's main job is to dispatch the data, not necessarily to process a complex response.

**Key API Functions:**

- fetch(url, { mode: 'no-cors', ... }): Using the 'no-cors' mode is a key characteristic, allowing the request to be sent to a third-party domain without requiring complex CORS headers, but at the cost of making the response body opaque to the script.
    

**When to Use It:**

- For sending notifications to services like Telegram, Discord, or Slack.
    
- To log events or analytics to an external data collection service.
    
- To trigger any stateless, remote action where a simple "sent" confirmation is sufficient.
    

**Examples in Practice:**

- **Chatbot** (.../38 Chatbot/): A clear example of this pattern. It provides a simple UI to type a message. The "Send" button triggers a fetch POST request to a hardcoded Cloudflare Worker URL. The request is sent with mode: 'no-cors', meaning the component can't read the worker's response but can confirm that the network request was dispatched. The worker is then responsible for the subsequent logic of forwarding the message to the Telegram API.
