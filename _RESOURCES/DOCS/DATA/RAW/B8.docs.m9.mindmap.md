





# Immersive Control & Input Management [ea_controls]

This module describes the advanced techniques for creating focused, game-like, or modal experiences within a component. The core pattern involves temporarily capturing and overriding Obsidian's default input handling, ensuring that user actions like keyboard presses and mouse movements are directed exclusively to the component, not to the wider application.

---

### 1. Obsidian Command & Hotkey Blocking

**What it does:** This is a critical pattern for creating truly immersive applications. It temporarily disables or intercepts Obsidian's native command palette and global hotkeys. When this mode is active, user input (like WASD for movement, Cmd/Ctrl+S, or even modifier keys like Alt and Meta) controls the component itself, rather than triggering global Obsidian actions like opening files, searching, or closing panes. This is achieved by programmatically overwriting parts of the app.commands API upon focus and restoring them on blur.

**Key Implementation Primitives:**

- dc.app.commands.commands = {}: Temporarily clearing the global command registry.
    
- dc.app.commands.executeCommandById = () => false: Overwriting the command execution function to block calls.
    
- event.preventDefault() & event.stopPropagation(): Used within keydown event listeners to stop the event from propagating to Obsidian.
    
- ref.current.focus(): Programmatically setting focus on the component's container to activate the blocking logic.
    
- ref.current.requestPointerLock(): A browser API used in game-like scenarios to capture all mouse movement for camera control, hiding the cursor.
    

**When to Use It:**

- When building a game or 3D world where standard keys (W, A, S, D, Space) are needed for character movement.
    
- To create a "focus mode" that prevents accidental hotkey triggers while a user is in a specific workflow.
    
- For modal dialogs that must be interacted with before the user can return to the main application (e.g., license agreements, critical confirmations).
    
- In any component where you need to define custom keyboard shortcuts that would otherwise conflict with Obsidian's native hotkeys.
    

**Examples in Practice:**

- **World888**: This component provides a masterclass in this pattern by abstracting the logic into a reusable preventDefaultInputs module.
    
    - The main WorldView component has a tabIndex to be focusable and calls handleFocus and handleBlur from the module.
        
    - The preventDefaultInputs module itself performs the direct manipulation of dc.app.commands to disable and restore Obsidian's command system when the 3D world gains or loses focus.
        
- **GameEngineBuild**: Implements this pattern from scratch for a first-person experience.
    
    - It uses canvasRef.current.requestPointerLock() to capture mouse input for camera control.
        
    - Its custom registerKeyListeners function attaches a keydown listener directly to the window, which calls e.preventDefault() on keys like Space to prevent the default browser action (scrolling) and ensure the input is used for jumping within the game.
        
- **LicenseAgreement**: A perfect example of using this pattern for a modal UI.
    
    - When the agreement component becomes active (isActive), it applies the command blocking logic to prevent the user from closing the pane or using hotkeys to navigate away.
        
    - It programmatically focuses its own container (ensureFocus) to maintain input capture until the user has completed all required tasks and clicked the "Proceed" button.
        
- **ExternalInputBlocker**: This is a minimal, focused reference implementation. Its sole purpose is to demonstrate the core logic of capturing focus (handleFocus), overriding dc.app.commands, and then restoring everything on blur (handleBlur). It's an excellent starting point for understanding the fundamental mechanics of the pattern.
